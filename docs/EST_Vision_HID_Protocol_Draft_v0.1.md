# EST 视觉虚拟传感器 HID 协议草案

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档版本 | 0.1 草案 |
| 更新日期 | 2026-09-07 |
| 当前状态 | 待下位机确认，尚未实现 |
| Studio 基线 | EST Studio 2.8.35 工作区 |
| 已检查固件协议 | `1.29` |
| 目标 | 电脑端 YOLO 将一个主要目标的类别、置信度和位置发送给 EST，作为虚拟传感器供用户程序读取 |

本文只整理现有通信链路并提出最小协议。当前阶段不接入 YOLO、不增加积木、不控制电机、不修改固件，也不发送模拟视觉数据。

## 2. 设计结论摘要

建议第一版采用以下方案，所有编号在下位机确认前均为暂定：

1. 沿用现有 EST HID 逻辑帧，不另建 USB 接口，不占用物理传感器端口 `1-4`。
2. 暂定命令 `0x28` 为 `VISION_SENSOR_COMMAND`；检查到的固件命令目前使用到 `0x27`，但 `0x28` 是否可正式分配仍需下位机确认。
3. 暂定协议从 `1.29` 递进到 `1.30`，使用当前 32 位能力字段的 bit 30 表示 `vision-input`。
4. 第一版每次只发送一个“主要目标”，即 YOLO 阈值和 NMS 处理后置信度最高的目标；多目标列表留给后续协议版本。
5. 目标位置使用归一化边界框中心点和宽高，不发送摄像头原始分辨率。
6. 上位机目标发送频率为 `10 Hz`，硬上限 `15 Hz`；采用“只保留最新一帧”的合并队列，禁止积压视觉帧。
7. 每个有效样本带有效期，建议默认 `500 ms`。下位机按接收时刻计时，超时后自动变为无效。
8. 每个写入、清除和状态请求都返回同命令 ACK，适配 Studio 当前严格串行的请求-响应模型。
9. 下载期间暂停视觉发送；运行成功后恢复；停止先取消待发视觉帧，再优先发送程序 STOP，最后清除视觉状态。
10. 当前固件运行 MicroPython 时会丢弃除 `0x24` 外的命令。固件必须明确放行视觉命令，否则运行中的程序无法读取电脑端视觉数据。

## 3. 已有 HID 协议审计

### 3.1 USB 与报告尺寸

| 项目 | 当前值 |
| --- | --- |
| USB VID | `0x0483` |
| USB PID | `0x5750` |
| Windows HID Report ID | `0`，`node-hid.write()` 时由上位机放在报告首字节 |
| 旧报告数据区 | `64` 字节 |
| 高速报告数据区 | `1024` 字节 |
| 单帧最大载荷 | `1010` 字节 |
| 固件 HID IN 队列深度 | `4` 个报告 |

本草案的最长逻辑帧只有 29 字节，可完整放入 64 字节和 1024 字节两种报告，不需要分片。

### 3.2 现有逻辑帧

主机到设备：

```text
68 11 CMD LEN_L LEN_H PAYLOAD... CHECKSUM 16
```

设备到主机：

```text
68 21 CMD LEN_L LEN_H PAYLOAD... CHECKSUM 16
```

| 字段 | 长度 | 说明 |
| --- | ---: | --- |
| 帧头 | 1 | 固定 `0x68` |
| 方向 | 1 | 主机 `0x11`，设备 `0x21` |
| 命令 | 1 | `uint8` |
| 载荷长度 | 2 | `uint16 LE` |
| 载荷 | N | 最多 1010 字节 |
| 校验 | 1 | 从帧头到载荷末尾逐字节求和，再取低 8 位 |
| 帧尾 | 1 | 固定 `0x16` |

逻辑帧写入 HID 报告后，报告剩余位置补零。所有本草案新增多字节整数都使用小端序。

### 3.3 与本功能相关的现有命令

| 命令 | 用途 |
| ---: | --- |
| `0x01` | 心跳并读取 6 字节固件版本 |
| `0x19` | 设备状态、协议版本、能力位、物理端口和电量 |
| `0x24` | RAM Python 状态、上传、运行、停止和清除 |
| `0x25` | 持久化程序槽位状态、保存、加载和清除 |
| `0x27` | 音频资源写入 |
| `0x28` | 本草案建议的视觉虚拟传感器命令，尚未分配 |

不建议把视觉信息塞入 `0x18 INPUT_SENSOR` 或 `0x19 DEVICE_STATUS`：现有四个传感器槽对应实体端口，状态载荷也只有固定的 72/76 字节格式。独立命令可以避免改变普通传感器和旧程序语义。

### 3.4 Studio 当前发送流程

```text
HID.devices()
→ 过滤 VID/PID
→ 打开唯一设备路径
→ 0x01 心跳读取固件版本
→ 0x19 读取设备状态
→ 后续所有命令进入同一 Promise 串行队列
→ 写完完整逻辑帧
→ 等待并校验同命令号响应
```

关键约束：

- `EstDeviceService` 只有一条 `commandQueue`，同一时间只允许一个请求-响应事务。
- 普通请求超时为 `2000 ms`；底层每次 HID 读取最多阻塞 `250 ms`。
- 上传 Python 时，`0x24 BEGIN`、每个 `0x24 CHUNK`、`0x25 SAVE` 都等待响应后才继续。
- Studio 正常约每 3 秒刷新连接状态；程序运行期间约每 10 秒刷新，并优先查询 `0x24` 程序状态。
- 当前读取循环只接受正在等待的命令号；协议不依赖设备主动推送数据。
- 视觉发送不能让每一帧直接排入普通 FIFO，否则下载期间会累积大量过时帧，并推迟 STOP。

### 3.5 当前固件的必要改动点

检查到当前固件在逻辑帧入口存在以下运行期门禁：

```c
if (est_micropython_program_is_executing() &&
    logical_frame[2] != PYTHON_PROGRAM_COMMAND) {
    return;
}
```

这意味着程序运行时，`0x19` 以及未来的视觉命令都会被直接丢弃且没有 ACK。视觉虚拟传感器要工作，下位机至少需要将视觉命令加入运行期白名单，并保证 ACK 和有效期计时在 MicroPython 运行时仍能执行。

## 4. 建议命令与能力声明

以下值均为待确认建议值：

```text
VISION_SENSOR_COMMAND          = 0x28
DEVICE_CAPABILITY_VISION_INPUT = 1 << 30
DEVICE_PROTOCOL_MAJOR          = 1
DEVICE_PROTOCOL_MINOR          = 30
VISION_SCHEMA_VERSION          = 1
```

能力位 bit 30 是当前 32 位能力字段中的下一个空位，不需要扩大 `0x19` 状态载荷。Studio 后续只对报告该能力的固件开放视觉积木和视觉数据发送；普通程序不要求该能力，不应被误拦截。

## 5. 最小消息格式

### 5.1 Action

| Action | 名称 | 主机载荷长度 | 作用 |
| ---: | --- | ---: | --- |
| `0x00` | `STATUS` | 4 | 查询虚拟视觉传感器状态 |
| `0x01` | `UPDATE` | 22 | 写入一个有效主要目标 |
| `0x02` | `CLEAR` | 8 | 立即清除目标，表示当前没有可靠检测结果 |

第一版只支持 `sensor_id = 0`。保留 `sensor_id` 是为了后续可以增加多个视觉流或多个目标筛选器，而不改变帧结构。

### 5.2 `STATUS` 主机载荷

| 偏移 | 类型 | 字段 | 值/说明 |
| ---: | --- | --- | --- |
| 0 | `u8` | action | `0x00` |
| 1 | `u8` | schema | `0x01` |
| 2 | `u8` | sensor_id | 第一版固定 `0` |
| 3 | `u8` | reserved | 固定 `0` |

### 5.3 `UPDATE` 主机载荷

| 偏移 | 类型 | 字段 | 范围/说明 |
| ---: | --- | --- | --- |
| 0 | `u8` | action | `0x01` |
| 1 | `u8` | schema | `0x01` |
| 2 | `u8` | sensor_id | 第一版固定 `0` |
| 3 | `u8` | reserved | 固定 `0` |
| 4 | `u32 LE` | sequence | 本次 HID 连接内递增；仅用于 ACK 对应和诊断 |
| 8 | `u16 LE` | ttl_ms | 建议允许 `300-2000`，默认 `500` |
| 10 | `u16 LE` | class_id | `0-65534`；`65535` 保留为无效值 |
| 12 | `u16 LE` | confidence_permille | `0-1000`，例如 923 表示 92.3% |
| 14 | `u16 LE` | center_x_10000 | `0-10000`，图像左边为 0，右边为 10000 |
| 16 | `u16 LE` | center_y_10000 | `0-10000`，图像顶部为 0，底部为 10000 |
| 18 | `u16 LE` | width_10000 | `0-10000`，目标框宽度占图像比例 |
| 20 | `u16 LE` | height_10000 | `0-10000`，目标框高度占图像比例 |

坐标必须相对于送入模型并完成旋转/镜像校正后的可见图像。下位机只保存定点整数，不处理摄像头分辨率、缩放和方向。

`class_id` 是模型类别表中的数字，不在高频 HID 帧内重复传输类别名称。第一版必须固定一份类别映射，或由 Studio 保证“生成程序时的类别表”和“运行 YOLO 时的类别表”一致。自定义模型如何标识类别表，列入下位机与产品层确认项。

### 5.4 `CLEAR` 主机载荷

| 偏移 | 类型 | 字段 | 值/说明 |
| ---: | --- | --- | --- |
| 0 | `u8` | action | `0x02` |
| 1 | `u8` | schema | `0x01` |
| 2 | `u8` | sensor_id | 第一版固定 `0` |
| 3 | `u8` | reason | 见下表 |
| 4 | `u32 LE` | sequence | 本次 HID 连接内递增 |

| reason | 含义 |
| ---: | --- |
| `0` | 初始化或手动清除 |
| `1` | 当前图像没有达到阈值的目标 |
| `2` | YOLO、摄像头或视觉进程停止/异常 |
| `3` | Studio 正常断开设备或退出 |
| `4` | 用户程序停止 |
| `5` | 下载/运行流程切换，清除上一会话数据 |

### 5.5 设备响应载荷

`STATUS`、`UPDATE` 和 `CLEAR` 都返回同一个 16 字节状态载荷：

| 偏移 | 类型 | 字段 | 说明 |
| ---: | --- | --- | --- |
| 0 | `u8` | schema | `0x01` |
| 1 | `u8` | result | `0` 拒绝，`1` 成功，`2` 忙 |
| 2 | `u8` | state | `0` 已清除/从未写入，`1` 有效，`2` 已过期 |
| 3 | `u8` | error | 错误码 |
| 4 | `u8` | sensor_id | 第一版为 `0` |
| 5 | `u8` | accepted_action | 本次处理的 action |
| 6 | `u16 LE` | reserved | 固定 `0` |
| 8 | `u32 LE` | sequence | 最近接受的 `UPDATE/CLEAR` 序号 |
| 12 | `u16 LE` | age_ms | 距最近有效 UPDATE 的设备端时间，最大饱和为 `65535` |
| 14 | `u16 LE` | ttl_ms | 当前样本有效期；无样本时为 `0` |

建议错误码：

| error | 含义 |
| ---: | --- |
| `0` | 无错误 |
| `1` | 不支持的 action |
| `2` | 不支持的 schema |
| `3` | 载荷长度错误 |
| `4` | 字段超出范围 |
| `5` | 不支持的 sensor_id |
| `6` | 内部状态暂时不可写 |
| `7` | 运行期命令被阻止；正式支持视觉的固件不应因 Python 正在运行而返回此错误 |

`UPDATE` 不进行旧帧自动重试。若 ACK 超时，上位机丢弃该帧并在下一次调度发送最新结果，避免延迟帧覆盖新结果。

## 6. 样本选择与有效期

### 6.1 第一版主要目标

第一版协议不发送检测列表。Studio 对一次 YOLO 推理结果执行：

1. 应用模型置信度阈值和 NMS。
2. 若没有目标，发送一次 `CLEAR(reason=1)`。
3. 若有目标，选择置信度最高的目标；置信度相同时选择面积较大的目标。
4. 将该目标编码为一个 `UPDATE`。

未来若确认需要同时读取多类或多个实例，再新增批量 action 或启用多个 `sensor_id`，不在 v1 中预埋可变长列表。

### 6.2 有效期规则

- 下位机收到并接受 `UPDATE` 的时刻记为 `received_at_ms`。
- 当 `now_ms - received_at_ms >= ttl_ms` 时，状态从 `valid` 原子切换为 `expired`。
- 过期后，用户程序必须先看到“无有效目标”，不能继续把旧类别和旧坐标当成新检测。
- `CLEAR` 立即使状态变为 `empty`，不等待 TTL。
- Studio 崩溃、USB 拔出或 YOLO 卡死时，即使无法发送 CLEAR，TTL 仍是最终失效保障。
- TTL 必须使用固件单调时钟，不依赖电脑时间，也不能依赖 Python 用户程序主动调用刷新。
- Studio 不把同一张旧图像反复当作新样本续期；只有新的推理结果可以发送新的 UPDATE。

若电脑推理速度明显低于 10 Hz，Studio 可以把 `ttl_ms` 设置为最近推理周期的约 3 倍，但不得超过协议确认的上限；建议范围仍为 `300-2000 ms`。

### 6.3 无效状态的读取建议

建议固件运行时提供独立有效位，用户先判断有效性，再读取数值。状态无效时建议返回：

```text
valid      = false
class_id   = -1
confidence = 0
x/y/w/h    = 0
```

具体 MicroPython API 名称及无效值必须由下位机确认，本草案不冻结 API。

## 7. 发送频率与流控

### 7.1 频率

| 项目 | 建议值 |
| --- | ---: |
| 常规发送频率 | `10 Hz` |
| 硬上限 | `15 Hz` |
| 常规间隔 | `100 ms` |
| 视觉请求 ACK 超时 | `250 ms`，待真机确认 |
| 默认 TTL | `500 ms` |

发送频率是 HID 更新频率，不要求 YOLO 必须固定帧率。推理快于 10 Hz 时丢弃中间旧结果；推理慢于 10 Hz 时只在新结果产生时发送，并依靠 TTL 正确表达停滞。

### 7.2 Studio 合并队列

视觉发布器不得对每个 YOLO 结果调用现有普通 `request()` 并无限加入 `commandQueue`。后续实现应使用以下状态：

```text
latestVisionSample  最后一个尚未发送的新结果
visionInFlight      当前是否有一个 0x28 请求正在等待 ACK
visionPaused        下载、运行准备、停止或固件更新期间暂停
controlOperation    当前是否有下载/运行/停止等控制操作
```

规则：

1. 新推理结果覆盖 `latestVisionSample`，队列中最多保留一个待发样本。
2. 同一时间最多有一个视觉请求在途。
3. 控制操作开始时清空待发样本，禁止继续排入视觉请求。
4. STOP 的优先级高于视觉；它最多等待一个已在途视觉请求结束，不能等待视觉 backlog。
5. ACK 超时不重发旧样本；记录错误并等待下一份最新结果。
6. 所有 HID 写入仍由主进程 `EstDeviceService` 统一管理，渲染进程和未来 YOLO 子进程不得直接打开同一 HID 设备。

## 8. 与下载、运行和停止的兼容流程

### 8.1 只下载，不运行

```text
暂停视觉发送并丢弃待发帧
→ 如有旧程序，沿用现有 0x24 STOP 清理
→ 0x24 BEGIN/CHUNK 上传
→ 0x25 SAVE 保存槽位
→ 保持视觉发送暂停
```

下载期间不发送 `0x28`，避免影响源码分片、CRC 校验和 Flash 保存。只下载完成后设备没有运行用户程序，虚拟视觉传感器不需要持续更新。

### 8.2 下载并运行

```text
暂停视觉并丢弃待发帧
→ 停止旧程序
→ 上传并保存新程序
→ 0x28 CLEAR(reason=5)
→ 若已有新鲜检测，可先发送一次 0x28 UPDATE
→ 0x24 RUN
→ RUN ACK 成功后恢复 10 Hz 视觉发送
```

如果运行前没有新鲜检测，只发送 CLEAR。用户程序启动后读到“无有效目标”是正常状态，首个推理结果到达后再变为有效。

视觉 UPDATE 或 CLEAR 失败不应让普通、未使用视觉能力的程序无法运行。对明确使用视觉积木的程序，Studio 后续应在下载前检查 `vision-input` 能力；运行期短暂没有目标属于数据状态，不属于固件不兼容。

### 8.3 停止

```text
立即停止视觉调度
→ 丢弃 latestVisionSample
→ 等待至多一个在途视觉请求结束/超时
→ 优先发送 0x24 STOP
→ 轮询 0x24 STATUS 直到程序结束
→ 0x28 CLEAR(reason=4)
```

停止按钮仍只终止用户程序，不发送电机控制命令。电机安全停止继续由现有下位机程序停止流程负责。

### 8.4 状态刷新

- 视觉运行期间，`0x28` 与现有 `0x24` 程序状态请求共用串行队列。
- Studio 当前运行期状态刷新间隔约 10 秒，不需要为了视觉提高 `0x19/0x24` 轮询频率。
- 设备不主动发送视觉数据；所有 ACK 都对应一个主机请求，避免响应命令交叉。
- 固件 IN 队列深度为 4；主机一次只保留一个请求在途，正常情况下不会填满该队列。

## 9. 断线与异常处理

| 场景 | Studio 行为 | 固件行为 |
| --- | --- | --- |
| YOLO 没有目标 | 发送一次 `CLEAR(reason=1)` | 立即失效 |
| 摄像头/YOLO 异常 | 停止调度并发送 `CLEAR(reason=2)` | 立即失效 |
| Studio 正常退出/断开 | 尝试 `CLEAR(reason=3)`，再关闭 HID | 立即失效；未收到 CLEAR 时由 TTL 兜底 |
| USB 直接拔出 | 清空本地在途和待发状态，不自动续传 | 最迟在 TTL 后失效 |
| Studio 崩溃 | 无法保证 CLEAR | 最迟在 TTL 后失效 |
| ACK 单次超时 | 不重发旧帧，下一周期发送最新帧 | 保持已有样本直到 CLEAR/TTL |
| 连续 ACK 超时 | 暂停视觉并触发现有连接诊断 | 不执行任何电机动作 |
| 重新连接 | 序号从 1 重新开始，先 CLEAR，再允许 UPDATE | 打开新会话并清除旧样本 |
| 用户程序异常退出 | 停止视觉并清除 | 视觉状态失效；不改变现有异常信息 |

无论视觉状态如何变化，固件都不能因为“未识别到目标”自动控制电机。用户程序必须显式读取虚拟传感器并决定动作。

## 10. 固件实现约束建议

1. 在运行期命令白名单中允许 `VISION_SENSOR_COMMAND`，不能只允许 `PYTHON_PROGRAM_COMMAND`。
2. HID 处理只校验并写入一个固定大小快照，不在 USB 回调里执行 Python 回调、模型逻辑或电机逻辑。
3. USB 写入快照与 MicroPython 读取快照之间必须原子化；建议短临界区复制整个结构，或使用双缓冲和 generation 序号。
4. TTL 计时必须在用户 Python 忙碌或异常时仍运行。
5. ACK 必须在程序运行时及时进入现有 HID IN 队列。
6. 视觉更新不能清除、重启或改变 Python 程序状态。
7. `0x19` 继续使用当前 72/76 字节状态格式，只新增能力 bit 30，不追加高频视觉数据。
8. 旧固件不认识 `0x28` 时 Studio 不发送该命令；普通下载、运行、停止流程保持原样。
9. 视觉状态只保存在 RAM，断电、复位、USB 重新枚举和固件更新后必须无效。

## 13. 协议确认后的联调验收建议

1. 旧固件不报告 `vision-input` 时，Studio 不发送 `0x28`，普通程序仍可下载和运行。
2. 模拟发送一个 UPDATE 后，STATUS 能返回相同 sequence、valid 状态和合理 age。
3. 用户程序运行时连续 10 Hz 更新 5 分钟，无 HID IN 队列溢出、无程序状态异常。
4. UPDATE 停止后，在 TTL 到期时虚拟传感器自动失效。
5. CLEAR 后立即失效，不保留旧类别供程序误读。
6. 30 FPS 模拟数据输入时，HID 仍最多发送 10-15 FPS，内存和命令队列不持续增长。
7. 视觉模拟持续产生数据时执行下载，视觉帧不插入 `0x24/0x25` 分片流程，源码 CRC 和槽位保存正确。
8. 点击运行时，先清理旧视觉状态，再启动程序并恢复发送。
9. 点击停止时，STOP 不被视觉帧积压；停止完成后视觉状态被清除。
10. USB 拔出或 Studio 进程结束后，设备最迟在 TTL 到期时报告无目标。
11. 重新连接后先 CLEAR，旧 sequence 和旧目标不会复活。
12. 普通不含视觉积木的程序完全沿用现有兼容门禁和运行流程。

## 14. 本阶段明确不做

- 不接入摄像头或 YOLO 推理。
- 不定义模型下载、模型切换和 GPU/CPU 选择。
- 不实现多目标列表、跟踪 ID、分割掩码、关键点或图像传输。
- 不新增视觉积木和生成器。
- 不修改下位机 runtime、HID parser 或能力位。
- 不让视觉结果直接控制电机。
- 不在协议确认前发送 `0x28` 模拟数据。
