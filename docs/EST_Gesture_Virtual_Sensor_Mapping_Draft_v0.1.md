# EST 手势到视觉虚拟传感器映射草案

日期：2026-09-09。版本：0.1，待上下位机确认，尚未接入发送。

## 1. 范围与依据

采用当前独立 MediaPipe Hands 识别结果，不使用 YOLO，不训练模型。人体姿态、面部动作继续保留在电脑验证页，本草案不把它们混入手势流。不新增积木、不修改 HID 帧、不修改固件。

依据当前工作区，而非仅依据早期草案：

- `src/main/est/constants.js`：协议主版本 1、次版本至少 30、bit 30 `vision-input`、命令 `0x28`。
- `src/main/est/protocol.js`：schema 1，仅允许 `sensor_id=0`；UPDATE 22 字节、CLEAR 8 字节、STATUS 4 字节。
- `src/main/est/device-service.js`：最新帧合并发送、运行状态门禁、暂停与清除机制。
- `src/renderer/est-vision/hand-results.js`：左右手映射及各自五帧手势投票；手消失立即清空历史。
- `src/renderer/est-vision/holistic-recognition.js`：现有规则手势类别。

`EST_Vision_HID_Protocol_Draft_v0.1.md` 是历史设计依据，其中 YOLO、协议未实现等描述不代表当前工作区状态。用户已确认下位机完成视觉协议联调；本文未重新审计固件，不把新增类别约定视为固件已支持。

## 2. 最小方案与限制

电脑同时识别左右手，但现有设备槽一次仅保存一个目标。首版建议由用户选择发送对象：左手、右手、自动。默认右手；选择模式先属于电脑配置，不假定已有对应积木。

| 模式 | 选择规则 |
| --- | --- |
| 左手 | 仅发送使用者自己的左手；左手缺失则 CLEAR，不借用右手 |
| 右手 | 仅发送使用者自己的右手；右手缺失则 CLEAR |
| 自动 | 优先保留当前已选中的手；首次或丢失后两手均可用时优先右手 |

自动模式失去当前手时，先清除该目标；确认 CLEAR 成功后再采用另一只手的新鲜结果。不得同一 HID 槽逐帧交替左右手，以免下位机把两者当作同一连续目标。该切换状态机是后续待实现内容。

类别同时编码左右手及手势，只能描述当前目标。不能据此宣称支持“下位机同时读取左右手”或双手组合动作。若有该需求，应另行确认多个 sensor_id 或批量样本协议，不占用 reserved 字节。

## 3. 类别表（建议编号，待确认无冲突）

映射标识：`est-hand-gesture-v1`。编号永久固定，不随界面语言或列表顺序改变。当前协议不携带映射标识，双方必须约定一致后启用，不得与其他模型类别混用。

| 手势键 | 显示名称 | 左手 class_id | 右手 class_id |
| --- | --- | ---: | ---: |
| open_palm | 张开手掌 | 1101 | 1201 |
| closed_fist | 握拳 | 1102 | 1202 |
| thumbs_up | 点赞 | 1103 | 1203 |
| pointing_up | 食指指向 | 1104 | 1204 |
| victory | 胜利手势 | 1105 | 1205 |
| other | 其他手势 | 1106 | 1206 |

“其他手势”表示手确实存在，但不属于已定义规则，仍发送位置；“未检测”必须 CLEAR，不编码成 other，也不发送 `class_id=65535`。不新增未经验证的 OK、数字手势等类别。

当前手势输出是几何规则结果，并非经过训练的手势分类器。规则名称不保证任意朝向、遮挡或交叉动作下均可靠。五帧投票仅稳定手势，不能为已消失的手延长存在状态。

## 4. 位置、左右手与镜像

左右指使用者自身解剖学左右，不是预览画面左右。沿用 `separateHands` 的输入镜像修正，不能再做第二次交换。

建议 HID 坐标与当前镜像预览一致：左上角为 (0,0)，向右 X 增大，向下 Y 增大。当前模型输入未镜像，故每点 `x_view=1-x_model`、`y_view=y_model`；若后续输入本身已镜像，不得重复翻转。

对选中手的全部 21 个关键点取包围框，先验证坐标有限，再把边界裁剪到 [0,1]。宽或高为零则视为无效目标，不发送退化框。不用手腕点代替包围框中心。

```text
cx = (xmin + xmax) / 2
cy = (ymin + ymax) / 2
w  = xmax - xmin
h  = ymax - ymin
centerX = round(cx * 10000)
centerY = round(cy * 10000)
width   = round(w  * 10000)
height  = round(h  * 10000)
```

全部整数限制在 0..10000。预览等比缩放的留白不属于坐标系；摄像头切换、旋转或镜像策略变化时先 CLEAR 并重置状态。下位机需确认与原协议的坐标方向约定一致。

## 5. 置信度：必须确认，不能伪造

现有 `handednessScore` 是左右手分类分数，不是手存在概率，也不是点赞等手势的正确率。规则中的固定 confidence 数值同样不能当作真实模型概率发送。

建议首版将 `confidencePermille=0` 约定为“该手势映射不提供校准置信度”，有效性仅由状态 VALID/CLEAR/EXPIRED 判断。当前编码器允许 0，但不意味着下位机及其用户 API 已认可此语义。

这是上线阻塞确认项：如果下位机把 0 必定解释为无效或低于阈值，则不能采用该方案，也不能用 1000 或左右分类分数蒙混替代。需另行协商明确的分数语义或协议扩展。在确认前保持本地验证，不发送正式手势数据。

电脑诊断仍可单独显示左右分类分数、五帧投票比例，但标明各自含义；它们不写入本草案的置信度字段。

## 6. 帧与发送生命周期

复用现有编码器，不自行构造第二套 HID 发送队列。以下是待实现的适配策略，未修改当前发送器。

| 字段 | 建议值/来源 |
| --- | --- |
| action / schema / sensorId | UPDATE=1 / 1 / 0 |
| reserved | 0 |
| sequence | 由设备服务按连接管理，不使用摄像头帧号替代 |
| ttlMs | 500；固件从接收时刻开始计时 |
| classId | 选中手侧别 + 稳定手势，查固定表 |
| confidencePermille | 暂定 0，须先确认第 5 节 |
| centerX / centerY / width / height | 同一最新识别帧内选中手的包围框 |

示例：右手张开，中心 (0.7,0.4)，大小 (0.2,0.3)：

```json
{"sensorId":0,"ttlMs":500,"classId":1201,"confidencePermille":0,"centerX":7000,"centerY":4000,"width":2000,"height":3000}
```

该对象不含 sequence，交给现有服务分配。不是新增协议或已启用发送样例。

- 本地识别目标约 30 FPS；HID 按当前 100 ms 间隔，最高约 10 Hz，ACK 耗时可能使实际速率更低。
- 每次完成真实推理都更新最新结果，即便类别未变也需新鲜样本维持 TTL。仅保留最新一帧，不堆积所有摄像头帧。
- 建议适配层对采集时间年龄超过 200 ms 的结果不再发布，并触发来源超时清除。不得反复发送冻结的旧帧来续期；采集时间须用单调时钟。
- 未检测到选中手：立即清空本地投票/待发 UPDATE，调度 CLEAR(reason=1)。已在途命令无法撤回，CLEAR 仍须等待串行事务完成，不能声称设备端零延迟。
- 摄像头关闭、权限拒绝、推理异常、帧源停滞：CLEAR(reason=2)，重置选择与历史。
- 程序停止：复用现有停止流程，取消待发帧，STOP 后 CLEAR(reason=4)，不得让视觉重试推迟停止。
- 下载或固件升级：暂停视觉发送并丢弃过期结果；恢复需重新获得新鲜帧，不重放暂停前缓存。
- 正常断开尽力 CLEAR(reason=3)；物理拔线无法保证送达，依赖设备 TTL 自动失效。重连先初始化 CLEAR，不自动运行程序。
- 无目标期间不重复刷 CLEAR；ACK 失败必须显式报告，依赖 TTL 兜底，不能假报已清除。UPDATE 失败不重发旧帧。

注意：当前服务存在 `_sendLatestVisionBeforeRunNow()`，会在 RUN 前预置一帧，而常规发送仅在运行期间调度。此行为与早期“运行后才 UPDATE”的文字不同。本草案不暗改该路径；接入前须明确是否保留预置帧，并验证程序第一条读取的行为。

## 7. STATUS 与固件确认清单

当前 STATUS 响应提供状态、序号、age、TTL，不回传目标类别或框，不能单靠 ACK 证明固件用户程序读到了正确手势。联调应由下位机提供已实现的读取方法和观测方式，不在本文虚构 runtime API 名称。

1. 确认 1101..1106、1201..1206 类别编号无冲突，识别该映射的启用方式是什么？
2. 确认单槽仅保留选中手可满足首版需求；是否明确不要求同时读取两手？
3. 是否接受 confidence=0 表示未提供校准概率，且 VALID 不因此变无效？既有程序如何避免把它当作低置信度？
4. 确认坐标以镜像预览为准；左右手类别仍是使用者自身左右。
5. CLEAR/TTL 失效后，固件读取类别、位置、有效状态分别返回什么？调用方是否必须先判断有效状态？
6. 提供实际 runtime 读取接口、数值单位、原子快照保证及未知类别处理规则。
7. 确认运行前预置帧策略，以及暂停、停止、物理断线、重连时的真实行为。
8. 确认摄像头真实数据与模拟器互斥；不得同时写 sensor_id=0。映射或发送对象切换须先清除旧会话。

以上语义确认前只保留草案，不接积木、不发送真实数据、不控制电机。

## 8. 后续联调验收

先做纯函数测试：所有类别、左右镜像、越界/NaN/退化框、固定手缺失、自动切换、过期帧和 CLEAR。再用已存在的模拟发送链路确认设备读值，最后接真实摄像头，模拟源与摄像头源互斥。

现场验证：左右手分别做六种手势；双手做不同手势时仅选中手被发送；选中手离开但另一手还在；镜像两侧位置；关闭摄像头；运行/停止/下载暂停；物理断线 TTL 与重连。记录识别 FPS、发送频率、ACK、有效状态和清除时间，不把摄像头 FPS 当 HID 发送频率。

此前现场识别约 29.5..29.9 FPS，双手阶段 210/210 帧同时检测到两手；用户确认中途做了点赞动作。离开阶段采样无残留，但用户标记晚于实际移手，不能据此计算精确清除延迟。以上只证明电脑端验证表现，不代表真实手势到固件链路已经验收。
