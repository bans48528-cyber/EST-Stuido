# EST 多类视觉输入协议对接草案 v0.2

状态：历史草案。线协议已经固化为协议 1.31、bit 31 和 schema 2；Studio 实现与
联调入口见 `EST_Vision_Multi_Target_Studio_Integration_2026-09-10.md`，字段定义以
固件仓库 `docs/EST_Vision_Multi_Target_Protocol_V1.md` 为准。

## 本次界面行为

- 摄像头使用独立 Electron 窗口，不加载积木工作区，关闭窗口即停止采集和发送。
- 用户选择左手、右手、身体、面部后点击开始。按选择加载模型，左右手共用 Hands。
- 删除发送勾选、发送对象下拉框、RAM 测试程序和拔线测试入口。
- 单选兼容现有协议 1.30、vision-input 能力 bit 30、0x28 指令。
- 多选仍执行本地识别，但明确显示尚未向 EST 发送。禁止轮流把多类目标写入旧 sensorId=0 单槽。
- 未连接时保留本地识别，每秒至多检查一次连接缓存；重新连接后单选自动恢复发送。

## 目标

EST 同时保存左手、右手、身体、面部的最新结果。用户程序在一次循环内读取不同类型时，不因后写入的一类覆盖前一类。人体和面部不能通过手势类别值间接猜测。

## 建议消息语义

沿用既有 HID 帧、校验和请求应答机制；新增独立能力标识（建议名称 `vision-input-multi`）。协议版本、能力位位置、命令号/子操作码须由固件确认，不能仅凭版本号推断支持。

| 操作 | 建议内容 |
| --- | --- |
| STATUS | 是否支持多类、支持类型掩码、各类型有效标志、最近序号、剩余有效期 |
| UPDATE_FRAME | 帧序号、TTL、启用类型掩码、各类型有效掩码、最多四项结果 |
| CLEAR | 类型掩码和原因；支持清单项、全部清除 |

每项结果包含：目标类型（left/right/pose/face）、类别码、置信度、中心 X/Y、宽/高。数值量纲与 v0.1 一致：位置和尺寸 0..10000，置信度 0..1000。启用掩码与有效掩码必须分离，不能把“关闭识别”和“未检测到目标”混为一谈。

类别映射继续参考 `visual-classes.js` 与既有映射文档：左手 1101..1106，右手 1201..1206，面部 2100+动作位掩码，人体 3101..3107。关键点规则没有真实概率输出，置信度保持 0（未提供），不伪造模型置信度。

UPDATE_FRAME 是完整快照：缺失/无效目标立即使对应缓存无效，其余目标不受影响。四类同帧原子更新，不允许读取到半帧新数据和半帧旧数据。

若数据超出单个 HID payload，建议分片携带相同 frameSequence；固件集齐后一次提交。缺片或超时不提交半帧。分片数量、序号位宽、乱序与超时处理需固件确认。

## 时序与安全

- 摄像头识别仍以 30 FPS 为目标；USB 完整快照发送建议 10 Hz。
- 只保留最新快照，禁止排队积压旧帧；未发完的整帧处理方式需与分片实现共同确定。
- 帧采集至发送超过 200ms 即弃用；默认 TTL 500ms。
- 仅程序运行期间允许 UPDATE。停止程序、关闭摄像头窗口、摄像头断开和渲染进程退出时 CLEAR 全部。
- 窗口关闭在渲染侧释放 MediaStreamTrack，在主进程同步撤销发送租约；异常退出由主进程与 300ms 租约看门狗兜底。
- USB 断开后不重放旧结果，依赖固件 TTL 自动清除；重新连接后等待新快照。
- 程序下载、固件升级期间暂停全部视觉发送，恢复后仅发送新采集结果。

## 下位机需确认

1. 新能力位、协议版本和命令/子操作码；旧 0x28 单槽协议保持兼容。
2. 四类型缓存的标识、数据结构、内存预算和原子提交方式。
3. 单帧四项目标的载荷预算，是否需要分片；帧序号、超时与 ACK 规则。
4. 各类型 CLEAR、TTL、无目标和关闭类型的区别。
5. Python/运行时读取 API：按类型读取快照；返回有效位、类别、位置、置信度和序号。
6. 既有 `rt.vision_snapshot()`、单目标“类别/位置”积木的兼容默认值；新版积木是否增加目标类型下拉框。
7. 并发读取左/右手、面部、人体的测试矩阵，以及下载/运行/停止/断线时的行为。

## 下一阶段验收

确认线协议和运行时 API 后，接入多类快照发送与积木读取。验证：左右手不同手势与面部/姿态同时可读；一类消失仅清除该类；关闭窗口全部失效；不会因类别轮换使条件判断抖动。当前阶段不声称多类 HID 联调已完成。
